## 一句话总结

一篇偏"系统设计说明"的短文：编码智能体从文字里推断要有哪些物体、它们之间要发生哪些交互，然后**对每个物体同时规划几何表示、属性字段和规则**，按"够用就行"选最简表示（碰撞只要框，挥击要关节代理，精细接触才上局部网格）（**Build**）；运行中可以用文字改属性值，或者给已有世界**加新字段和新规则**（例如给"只能搬运铁和木头"的世界加磁性），先在状态副本上校验、再在仿真步边界提交，不相关状态保持不变（**Steer**）；外观用**按物体身份索引的纹理记忆**保存，只给白盒定义的物体建条目，物体材质或损伤被改时让对应纹理作废、只是位姿变化则保留（**Memorize**）。渲染器吃"提示词 + 白盒导出的深度或边缘 + 投影过来的已存外观"。目前**只有 12 个场景的定性结果**，没有任何定量数字，记忆消融和回访基准都写着"即将发布"；渲染器、编码智能体用的是哪个模型也没写。

## 要解决什么问题

- 视频世界模型即便加了视觉记忆，长时 rollout 仍会丢物体身份、违反物理一致性；而且"记住一帧画面"不等于"暴露决定物体下一步怎么反应的属性和规则"。
- 代码世界模型（CWM、PWM、CoDeR……）把状态和规则显式化，接上生成式渲染器后把"状态持久"和"渲染保真"分开了。但从文字搭世界还留着三个相互关联的问题：
  1. **物体怎么表示**：结构化模型要保留哪些信息，渲染器才能画出合法的交互？
  2. **行为怎么定义和修改**：运行中来了新需求，怎么改属性甚至扩能力，又不破坏已有状态？
  3. **外观怎么长期记住**：长 rollout 里交互和编辑不断累积，要保留没变的细节、反映变了的部分。
- 作者的回答：用同一套**物体定义**把这三件事串起来，让编码智能体对世界的了解同时指导仿真和视觉记忆。

## 方法

总览见 [[topics/papers/代码世界模型与神经渲染/1-10_2610.21283_Mallea.pdf#page=3|图 2（第 3 页）]]。三方分工：编码智能体建造和修改世界代码与记忆策略，运行时代码执行它们，生成式渲染器产出观测。

### 世界状态怎么用代码表示（§3.1）

- 输入：初始文字提示；运行中可选的用户动作 u_t（如 WASD 移动）和文字编辑 q_t。输出：视觉观测序列 I_t。
- 区分**可执行模型 M_t**（定义物体和规则）和**当前状态 S_t**（记录取值和关系）。每个物体有稳定身份、一种几何表示、一组有类型的属性。
- 编辑之间，运行时代码按固定仿真步推进：S_{t+1} = F_{M_t}(S_t, u_t)。没有用户动作时（u_t = ∅）世界照样推进、照样结算物体间交互。
- 术语：**interactions** 指白盒物体之间的作用，**actions** 指用户控制。
- 纹理库 T_t 与物理状态分开：物体离开视野只影响检索，物体本身继续存在和演化。

### 自适应构造：Build（§3.2，[[topics/papers/代码世界模型与神经渲染/1-10_2610.21283_Mallea.pdf#page=3|图 3，第 3 页]]）

| 交互需要 | 选择的表示 | 暴露的信息 |
|---|---|---|
| 碰撞、冲击 | 粗碰撞框（box proxy） | 位姿、包围范围 |
| 关节运动（挥击、格挡） | 关节代理（jointed proxy） | 关节角、限位 |
| 精细接触 | 局部网格（local mesh） | 表面、法线 |

- 这三种是**可组合的互补选择**，不是必须依次升级的阶段。
- 智能体对每个物体同时规划表示、属性和规则；一个**局部交互检查**判断几何能否提供规则所需的接触和运动，失败才做针对性细化，成功就保留简单表示。
- 不影响交互的外观细节留给渲染器。作者举的对照：光学装置场景用机械几何，战术场景用粗代理，二者都由渲染器补场景外观（图 6）。

### 可编程属性：Steer（§3.3，[[topics/papers/代码世界模型与神经渲染/1-10_2610.21283_Mallea.pdf#page=4|图 4，第 4 页]]）

- **按物体定义行为**：从计划的交互反推规则要读写哪些信息，选出对应字段。每个字段规定类型、单位、初值、允许的写入者；初值来自提示词、可得证据或明确的建模假设。
- **规则 = 事件 + 条件 + 更新**。例：锤击时几何提供接触，材质、刚度、损伤决定响应，于是改字段就改执行结果（陶瓷裂、橡胶压缩、钢不变——作者注明这是在设定好冲击和材质参数下的示意，材质名本身不决定物理结果）。字段检查和接触检查一起保证规则既有信息又有几何。
- **运行时扩展行为**：文字请求可能只改已有值，也可能需要新字段和新规则：(M_t⁺, S_t⁺) = Edit(M_t, S_t, q_t)。改值不动模型定义；扩展会修改定义并初始化新字段。
- **提交前校验**：在状态副本上检查字段类型和单位、规则依赖、不受影响的事实是否保留、相关的局部行为；通过后在**仿真步边界**提交（并重新核对版本），失败则保留原世界。需要新物理求解器的请求要先有经过验证的求解器扩展——作者用这一点区分"增加能力"和"调用已有能力"。
- 例（图 4b）：原世界只支持搬运铁片和木块；请求"加磁性"后加入磁响应字段和吸引规则，铁被吸、木头不动，已有物体的身份、位置、损伤都带入扩展后的世界。

### 物体纹理记忆：Memorize（§3.4，[[topics/papers/代码世界模型与神经渲染/1-10_2610.21283_Mallea.pdf#page=5|图 5，第 5 页]]）

- 纹理库按**物体身份**索引。每个条目存：可复用外观、有效表面覆盖、注册时所处的表示和外观相关状态。
- **只给白盒定义的物体建条目**，生成出来的背景不会自动存。纹理坐标跟着框的面、关节部件或网格表面走，所以记忆跟随所选表示。
- **检索**：编码智能体提供可见性规则，运行时代码做投影和遮挡计算、更新每个物体的 `visible` 字段；活动窗口只装可见物体，视野外条目保留。一个视频片段的检索范围覆盖其整条已提交相机轨迹上任意时刻可见的物体。
- **复用条件**由智能体根据每个物体的表示和外观相关属性定义，并随模型扩展而修订：
  - 材质或损伤编辑 → 受影响区域作废；
  - 位姿变化 → 可以保留物体局部纹理；
  - 表示变化 → 需要经过验证的表面映射，否则作废；
  - 视角相关的贴片 → 需要相容的观察方向。
- 相容区域按当前位姿投影成**带掩码的颜色条件**；没看过、不相容或对不准的区域不加约束。

### 渲染器与条件信号（§3.4，式 3）

- I_t = G(p_t, B_t, A_t)：
  - p_t：当前渲染提示词，反映最新世界状态；
  - B_t：白盒视图及选定的**深度或边缘**控制；
  - A_t：投影过来的已存外观（带掩码颜色条件）。
- 作者强调渲染器必须能接受外观条件，因为深度和边缘本身带不了颜色。
- **注册回记忆**：照 CoDeR 的"观测注册到表面"，用物体 ID、深度、相机几何把生成画面对应到白盒表面；只有可靠的对应才更新覆盖，含糊的匹配丢弃；新覆盖补充已有条目，有效观测刷新被编辑作废的区域。作者提醒：存的纹理是视觉证据，不保证是物体真实反照率。
- 复用纹理**不会恢复旧的世界状态**：图 5 里花瓶 A 复用原纹样，材质被改成金属的方块 B 刷新外观。
- 编辑影响到待渲染片段时，重新计算轨迹和条件。
- **骨干是什么、怎么训练或适配、是否流式、速度多少，论文都没有写**。

## 局限 / 存疑

- **目前只是设计 + 示意**：图 2 标注"示意图"，图 4 标注"机制示意"，图 5 明说是"AI 生成的机制示意，不是实验结果"。真正来自系统的只有图 6 的 12 个场景帧。
- **图 6 的白盒是事后调整过的**：图注写"左列第 2–4 行的白盒在视频生成之后调整过"，即展示的白盒帧不完全是生成时用的条件，读图时不能把上下两行当成严格的输入–输出对。
- **关键实现全部缺失**：编码智能体是哪个模型、白盒用什么引擎 / 框架、渲染器是哪个视频模型、是否微调、外观条件怎么注入（深度 / 边缘 + 带掩码颜色需要一个能接受这类输入的渲染器，作者自己也指出了这一要求），都没写。专题清单"渲染骨干：生成式渲染器"的写法与论文一致，没法更具体。
- **记忆的效率和一致性未测**：作者自己写"实际效率和一致性需要测量"；按物体存纹理、只检索活动物体的预算控制也没有数字。
- **纹理记忆只覆盖白盒物体**：背景等生成内容不进记忆，回访时背景一致性靠什么保证，没有讨论。
- **物理求解能力的边界**：材质响应靠手写规则（陶瓷裂、橡胶压缩），作者承认材质名不决定物理结果、新物理需要验证过的求解器扩展；能扩展到什么程度没有例子之外的证据。
- **评测计划**：提到会用 PROWBench（检查物理结果是否与程序记录一致）和延迟回访测试，但还没有结果。

## 与其他论文的关系

- **作者自己的定位**：引用 [[topics/notes/代码世界模型与神经渲染/1-01_CodeWorldModel|CWM]]（研究"最小充分代理"）和 [[topics/notes/代码世界模型与神经渲染/1-04_ProgrammableWorldModel|PWM]]（用状态增强的框平衡控制与视觉细节）作为表示选择的出发点；Mallea 改成**按物体、按交互需要**选表示，并把字段与规则一起规划。
- **外观记忆三条路**（Mallea 第 2–3 页的相关工作就是这么并列的）：
  - [[topics/notes/代码世界模型与神经渲染/1-05_CoDeR|CoDeR]]：把生成画面注册到世界表面（Mallea 的注册步骤直接沿用这一做法）；
  - [[topics/notes/代码世界模型与神经渲染/1-04_ProgrammableWorldModel|PWM]]：时间对齐和几何对齐的记忆；
  - [[topics/notes/代码世界模型与神经渲染/1-07_Oneira|Oneira]]：检索历史帧并按当前物体状态过滤。
  Mallea 的增量在于让**编码智能体按物体的属性和规则决定哪些纹理还能用**，物体定义改了，复用条件也跟着改。
- **运行时扩展规则**：与 [WorldCoder](https://arxiv.org/abs/2402.12275)、[GIF-MCTS（Generating Code World Models with LLMs guided by MCTS）](https://arxiv.org/abs/2405.15383) 这类"LLM 生成并修订转移程序"的工作同源；带类型字段的状态和 [MASS](https://arxiv.org/abs/2608.06257) 相似，区别是字段选择与交互规划、表示选择耦合。
- **与实时系统的距离**：[[mirros/notes/01_AgentGarten|AgentGarten]]、[[topics/notes/代码世界模型与神经渲染/1-11_Matrix-Game-4.0|Matrix-Game 4.0]]、[[topics/notes/代码世界模型与神经渲染/1-12_StreamRender-H3|StreamRender-H3]] 都有具体渲染器和延迟数字；Mallea 完全没涉及渲染器训练和速度，是在"世界一侧"做文章。
- **交互细节由谁负责**：Mallea 主张不影响交互的视觉细节都交给渲染器、交互所需几何留在代码里；[[topics/notes/代码世界模型与神经渲染/1-15_GameWM|GameWM]] 更进一步，让视频模型连交互的视觉实现也负责。两者对"代码该管多细"的取舍可以对照看。
- **渲染器候选**：需要一个同时吃几何（深度 / 边缘）和带掩码颜色条件的渲染器，[[topics/notes/代码世界模型与神经渲染/2-09_SolarRenderer|SolarRenderer]]（任意结构视频）、[[topics/notes/代码世界模型与神经渲染/2-06_AlayaRenderer-Flash|AlayaRenderer-Flash]]（G-buffer）是专题里可对照的方向，但 Mallea 没说用了哪个。
- **评测**：引用的 [PROWBench](https://arxiv.org/abs/2610.02205)（"视频模型是否渲染出程序规定的内容"）和专题里的 [[topics/notes/代码世界模型与神经渲染/3-04_WorldDraft|WorldDraft]] 是它承诺的定量评测最可能用到的工具。
- **同期相关**：[Recursive Code World Models](https://arxiv.org/abs/2609.11499)、[Code2Games](https://arxiv.org/abs/2610.05033)、[Code as Worlds](https://arxiv.org/abs/2608.27549) 都在"智能体写场景程序 / 交互逻辑"这一侧。

## 摘要（中文）

代码世界模型通过显式状态和可执行规则来表示世界动态。我们研究如何在这一形式下协调物体表示、行为修订和视觉记忆。我们提出 Mallea，一个从文字出发建造、操控和记忆世界的系统。编码智能体从提示词推断物体交互需求，联合规划物体的结构、属性和规则，偏好能支撑这些需求的紧凑表示。世界按规划的规则演化；可选的用户动作可以操控它，文字请求可以编辑属性或扩展能力，同时保留不受影响的状态。物体纹理记忆只为白盒定义的物体保存可复用的外观，并随这些物体的变化而调整。程序推进世界状态，生成式渲染器把当前结构与记住的外观结合起来。通过围绕同一组物体组织建造、干预和记忆，Mallea 让后续观测以最新状态和相容的外观为条件。
