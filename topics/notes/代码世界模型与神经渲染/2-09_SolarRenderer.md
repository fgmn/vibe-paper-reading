## 一句话总结

冻结 **MiniMax-H3 33B Ref2VA**，只加两个 LoRA，做一个"什么结构都能接"的渲染器：结构视频（灰盒、语义图、深度灰度、SMPL 人体…）走 H3 **原生的参考视频通路**，但每个结构潜帧拿**它所描述的目标潜帧的 RoPE 位置**（帧对齐），不加类型标识，只在提示词里用两句固定文字说明"这是什么、该跟随什么"，于是**一个控制 LoRA** 能读各种表示，包括训练时没见过的骨架、蜡笔画、点云、线框。加速则是拿现成的 DMAD 四步 LoRA 当起点，冻结控制 LoRA、只后训练加速 LoRA，用**结构引导的分布匹配**（老师沿"有结构 vs 去掉结构"的方向外推，w=1.5）——4 步渲 158 帧约 209 s，比 50 步（2,562 s）快 **12.3 倍**；块因果变体流式渲 768p，最高 28 FPS。训练数据是 8 个来源、帧对齐的 **136K 段**（约 243 小时）。在 Gemini 两两评判的 Elo 上，两个测试集都排第一（泛化基准 1441，与 LynnReal-Omni 并列；分布内 1510），16 种结构表示里有 11 种训练没见过。

## 要解决什么问题

游戏引擎和编码智能体能定好布局、运动、相机，但要把粗结构变成逼真视频，需要一个"跟随结构、补全结构没给的外观"的渲染器。作者认为现有渲染器有三个问题（第 2 页 §1）：

1. **控制绑定在某一种表示上**：引擎驱动的渲染器只吃自家引擎导出的那一种（白盒画面、语义图、代理视频、完整 G-buffer），通用可控生成器要么每种条件挂一个分支（ControlNet、Cosmos-Transfer），要么给每个输入打类型标签（LynnReal-Omni）。换引擎、换代理就得换模型。
2. **太慢**：大骨干要几十步去噪，而从头蒸馏一个这种规模的结构条件模型又贵又不稳（引的是 [[topics/notes/代码世界模型与神经渲染/2-06_AlayaRenderer-Flash|AlayaRenderer-Flash]]）。
3. **训练对很少逐帧对齐**：从真实视频估出来的条件带着估计器误差、和引擎代理不一样（引 [Proxy2World](https://arxiv.org/abs/2609.35023)）；已有的引擎配对数据都只来自单个引擎。

## 方法

总览见 [[topics/papers/代码世界模型与神经渲染/2-09_2610.28630_SolarRenderer.pdf#page=4|图 2，第 4 页]]。

### 任务定义（§3.1）

- 给结构视频 S（与目标视频同相机、同时间戳）、可选首帧 I、文字 c（总是有），建模 p(V | S, I, c)。四种输入组合：结构 + 首帧、只有结构、只有首帧、只有文字。
- 结构决定布局、几何、角色身体、运动、相机；材质、光照、细小结构留空，由首帧、文字和预训练先验补——作者称之为"受约束的补全"。

| 项目 | 内容 |
|---|---|
| 世界状态由谁维护 | 不在本文范围：结构视频由游戏引擎、仿真器、或编码智能体在引擎里搭出来（泛化基准大多是编码智能体在游戏引擎里做的），也可以从 YouTube 视频拟合 |
| 条件信号 | 任意结构视频，训练里见过 5 类：场景灰盒、近距深度灰度、语义分割图、物体掩码 + 骨架、SMPL 人体网格 |
| 骨干 | MiniMax-H3 33B Ref2VA，单流 DiT，全程**冻结** |
| 可训练部分 | 控制 LoRA φ（rank 384，所有块的注意力和 FFN 投影）+ 加速 LoRA ψ（rank 384） |
| 条件注入 | 结构潜变量进 H3 原生参考通路（文字、参考视频、音频、目标视频拼成一条全注意力序列），用目标帧的 RoPE 坐标 |
| 推理步数 | 4 步（双向）；块因果变体每块 4 步 |

### 帧对齐的参考条件（§3.2）

- **为什么不用 ControlNet 或通道拼接**：两者都要加从头训练的参数；走原生参考通路能继承 H3 读参考视频的能力。
- **问题**：原生参考 token 放在片段前面单独的时间段、有自己的空间网格，零样本的 H3 只把结构视频当"松散参考"，会照抄或换相机，而不是跟随结构。
- **帧对齐 RoPE**：第 k 个结构潜帧和第 k 个目标潜帧共享时间索引和空间网格；首帧编码成索引 0 的静态片段。同位置的 token 靠时间步区分——参考 token 保持骨干给参考输入的近乎干净的噪声水平，目标 token 带当前噪声。
- **无类型参考 + 固定描述**：序列里不加类型标识或模态嵌入，让 adapter 自己从结构视频里推断它约束了什么。提示词里每种表示配两句固定的话：一句定义（它显示什么），一句规则（跟随哪些属性、哪些视觉属性不许出现，例如"灰色外观不要出现"）。同一表示永远用同样的句子；新格式只需写新描述，不加参数、不重训。
- 提示词沿用 H3 的六段格式（主体定义、带任务前缀的摘要、保留分析、详细描述、音景、音乐）；场景描述由 Kimi K2.6 只看目标视频写，固定部分由代码按输入组合生成（附录 B，图 9–14 给了 6 个来源的真实示例）。

### 两阶段解耦训练（§3.3）

作者观察到：只要加速目标能更新控制 adapter，就会改变结构跟随方式；从头蒸馏又贵又不稳。所以在同一个冻结骨干上分两阶段：

| 阶段 | 训练什么 | 冻结什么 | 目标 | 关键超参（附录 A.1） |
|---|---|---|---|---|
| 1 控制适配 | 控制 LoRA φ | 骨干 | flow matching，只在目标 token 上算损失 | rank 384，158 帧、1344×768、24 fps，AdamW lr 1e-4，38,400 步，batch 4 |
| 2 加速适配 | 加速 LoRA ψ | 骨干 + φ | 结构引导的分布匹配（DMD 式） | rank 384，前 128 维用 DMAD 四步 LoRA 初始化、其余为零；fake score 是单独的 rank-128 LoRA（从老师初始化），每次生成器更新配 5 次 fake score 更新；lr 生成器 1e-5 / fake score 2e-6；800 次迭代，batch 4，w=1.5 |

- **起点**：因为骨干冻结，同一骨干上预训练好的四步 LoRA 可以直接和控制 LoRA 叠加（W = W0 + ΔW_ctrl + ΔW_acc）。叠上后已经能跟结构，但这个加速 LoRA 是对裸骨干蒸馏的，没见过控制模型。分工：φ 决定"渲什么"，ψ 决定"四步怎么走到结果"，所以只更新 ψ。
- **结构引导的分布匹配**（式 5–6，第 5–6 页）：老师是固定的阶段 1 全步模型。问题是全步采样的 H3 本身偏糊，叠了四步 LoRA 的学生反而比老师锐利，普通分布匹配会把学生拉回糊的方向，后训练完比起点还差。于是把老师的干净预测沿结构条件外推：`ẑ0^w = ẑ0(C) + (w−1)(ẑ0(C) − ẑ0(C∅))`，C∅ 是把结构视频 token 从参考序列里删掉（首帧和提示词不变）。类似 CFG，但只作用在结构条件上；w=1 退化为普通 DMD。代价是每次生成器更新多一次老师前向。
- 全部超参按单个 8 卡节点给出；发布的权重用更大 batch 训了同样多的样本。

### 块因果流式变体（§3.4）

- 片段切成每块最多 5 个潜帧。先用 teacher forcing 把双向控制 LoRA 改成块因果：每块看提示词、首帧、自己和前 5 块的结构、前 5 块的干净帧，看不到后面的块（19,200 步，batch 2，lr 3e-5）。
- 再冻结因果控制 LoRA，从双向四步 LoRA 初始化一个新的加速 LoRA，在学生自己的逐块 rollout 上后训练，老师用双向控制模型（w=1.5，1,600 次迭代，batch 1）。rollout 先无梯度生成，再整段按 teacher forcing 重放，让梯度同时管到"每块怎么生成"和"它怎么当后面块的上下文"。
- 推理：加速 LoRA 合并进骨干，控制 LoRA 保持挂载，每块 4 步，更新固定窗口 KV cache 后立即输出；配合不需要未来潜变量的 H3 流式 VAE 解码器，**768p 实时、最高 28 FPS**（硬件见"局限 / 存疑"）。

136K 段、约 243 小时、2,150 万帧；每段 158 帧、24 fps、768p。

| 来源 | 段数（图 3） | 条件 |
|---|---|---|

| [[topics/notes/代码世界模型与神经渲染/1-03_Magpie|Magpie]] | 30.6K | 人类玩 UE 游戏 + 同步灰盒 |
| CARLA | 25.3K | 语义分割（每类一种纯色） |
| 引擎录制 | 13.2K | 30 m 内深度渲成灰度，远处和天空为黑（另有掩码、位姿、骨架） |
| WildWorld（《怪物猎人 荒野》） | 8.5K | 只给首帧（结构标注和画面对不齐） |
| Blender | 6.7K | 场景白盒 |
| OmniWorld（3A 游戏，如《赛博朋克 2077》） | 4.1K | 只给首帧（背景块缺人和动态物体） |
| UnrealZoo（UE5） | 1.8K | 每个物体一种颜色的掩码 + 角色骨架 |

- **两项检查**（§4.2）：时间上，在一组帧偏移上算条件运动与目标运动的相关，峰值不在零偏移的删掉；空间上，比条件边缘在目标帧里的召回 vs 水平镜像后的召回，差距不够的删掉。另去重、去暗 / 低对比、去条件覆盖太少的片段，并人工抽查每个来源。
- **条件要足够**：一开始用画身体部位和物体的粗框，同步但缺几何，学不会形状；换成 30 m 内深度灰度。0.25 m 方块的更细代理闪烁高 4–7 倍，没采用。
- **审计数字**（附录 B.3）：Magpie 同步审计保留 32,027 / 44,266 段；引擎录制 84 个运动窗口中 80 个最佳偏移为零，深度 + 相机重投影误差中位数 0.06%；近距深度转换保留 13,700 / 13,702；YouTube 559 个视频留 137 个。
- **输入组合在建数据时就固定**：67.1% 结构 + 首帧、16.7% 只有结构、13.2% 只有首帧、2.9% 只有文字。不在训练时随机丢结构，因为提示词还会提到它、等于泄漏。

## 实验与关键数字

### 评测设置（§5.1、附录 A.2–A.3）

- **分布内测试集**：53 段，来自训练来源但录制、场景、地图不重叠，有真值视频。
- **泛化基准**：208 个用例，由 57 个结构视频、16 种表示构成，其中 11 种训练没见过（铅笔分镜、儿童蜡笔画、点云、体素、线框等）；**没有真值**；大多由编码智能体在游戏引擎里搭；按难度打标签（大运动、快相机、多人、风格化、夜景）。
- **主指标是 Gemini 3.8 Flash 两两评判**：输入结构视频、首帧、两个渲染结果（缩到 672×384、12 fps），回答画质、结构与运动跟随、首帧保持、总体偏好四问，正反两种顺序各判一次。按问题各拟合一个 Bradley–Terry 模型换算成 Elo（被比较方法均值 1000）。盲测人类评审"方向一致"。
- **自动分**：画质（DOVER、LAION 美学、VideoScore2）、稳定性（RAFT 光流 warp 残差、相邻帧 DINOv2 相似度）、控制（CoTracker3 轨迹误差、与结构的 Canny 边缘 F1）、首帧保持（最后一秒与首帧的 DINOv2 相似度），各映射到 0–100 再组内、组间平均。
- 对比方法各按自己发布的分辨率、帧数、采样器、步数跑，再缩放到 1344×768、24 fps 打分。

### 按难度、按表示（图 5、图 6、图 16，第 9、10、22 页）

- 每个难度标签上都优于所有对比方法，唯一例外是在**快相机**上输给自己的 50 步阶段 1 模型（−0.10）。对单引擎渲染器的净胜分 +0.67 到 +1.00，对 LongLive-Plug / DMAD 直接叠加的四步组合 +0.26 到 +0.68；未见表示上对 LongLive-Plug +0.46、对 Streaming CWM +0.70。
- 对"阶段 1 + LongLive-Plug"，每个表示大类都赢（+0.25 到 +0.69）。对自己的 50 步阶段 1：身体与姿态 +0.45、绘画 +0.41，但**场景灰盒 −0.22、SMPL 人体 −0.20、图像缓冲 −0.33**；细分到具体格式，彩色映射深度 −0.71、体素 −0.60、铅笔分镜 −0.38。

## 局限 / 存疑

- **"实时 28 FPS"的硬件没写**：§3.4 说 768p 实时、最高 28 FPS，但全文没给 GPU 型号和数量；209 s / 2,562 s 也只说"one GPU"。同骨干的 StreamRender-H3 要 8×GB200 才到每块 258 ms，所以 33B 骨干单卡 28 FPS 不太可能，多半是多卡（需核对代码仓库）。也没有报延迟（首块等待、按键到画面）。
- **主指标是 VLM 评委**：Elo 来自 Gemini 3.8 Flash，评委看的是 672×384、12 fps 的缩小版本；人类盲测只说"方向一致"，没报人数、用例数和一致率。泛化基准没有真值，且由作者用编码智能体搭建。
- **自动分和 Elo 的方向不一致**：结构引导后训练让 Elo 大涨，但自动总分反而从起点的 72.1 降到 71.6（表 10，稳定性和首帧保持下降）；泛化基准上最终四步模型自动分（71.6）与 50 步阶段 1 持平。作者在附录 C.2 承认这一权衡。
- **条件设计 / 数据消融的差距在噪声范围内**：各变体自动分在 65.9–66.5 之间，而"全部数据换个种子"就从 66.2 掉到 65.9。原生通路 vs ControlNet（66.5 vs 66.0）、共享 vs 独立 RoPE（66.2 vs 66.0）这些结论只有单次运行，证据偏弱。这些消融还用的是"早期数据配比"、半分辨率。
- **"16 种表示、11 种未见"的计数口径**：图 16 列出的未见格式有 SMPL+标记、2D 骨架（智能体 / 照片上）、Mixamo 重定向、铅笔分镜、蜡笔画、剪影、彩色映射深度、法线图、线框、点云、体素、3D 包围盒等 12–13 项，和"11 种"对不上，取决于怎么合并（需核对）。
- **正文里几处数字不在表中**：σ ≥ 0.9 调度（1107 vs 1096；1107 恰好也是表 2 里 LongLive-Plug w=2 的值）、1,200 次迭代（992）、加自蒸馏（1049），没有对应表格，无法核对是哪次拟合（需核对）。
- **对比的公平性**：对比方法按各自的分辨率跑再放大到 1344×768（Streaming CWM 的结构输入要缩到 336×192，StreamRender-H3 用 832×480），低分辨率方法在画质上吃亏；Wan2.2-VACE-Fun 只生成前 5 秒（81 帧 16 fps）。
- **在别人的演示用例上输给了"代码世界"系统**：对 CWM、AgentGarten、Code Video Model、EdenLive 净分为负（−0.33 到 −0.67）。这些是原作者精选的展示用例，对原作有利，但也说明"通吃各种表示"不等于在每家自己的表示上都更好。
- **对自己 50 步模型的退步**：四步模型在场景灰盒（−0.22）、SMPL 人体（−0.20）、彩色映射深度（−0.71）、体素（−0.60）上不如 50 步阶段 1；"加速几乎不损失"只在部分格式上成立。
- **流式变体的外观漂移**：作者承认后面的块会偏离首帧颜色；因果窗口只看前 5 块，没有更长的记忆机制。
- **数据小出入**：136K × 158 帧 ≈ 2,149 万帧，按 24 fps 约 249 小时，和文中"243 小时"差约 2%；YouTube 只留了 137 个视频却贡献 46.2K 段（平均每个视频 300 多段），图 3 标的是"Inputs per Source"，是段数还是输入数需核对。Magpie 审计后保留 32,027 段，图 3 写 30.6K，可能还有后续过滤。
- **引用小错**：正文说用 Kimi K2.6 写描述，引用的是 Kimi K2.5 技术报告。
- **单位 "LIGHTSPEED"**：论文只写这个名字，没写全称（需核对是否为腾讯光子工作室群 LightSpeed Studios）。

## 摘要（中文）

游戏引擎和编码智能体能够指定场景的布局、运动和相机，但要把这种粗糙结构变成逼真视频，需要一个既跟随结构、又补全结构未规定的外观的渲染器。现有渲染器绑定于某一个引擎的表示，需要几十步去噪或自己一套代价高昂的蒸馏，而且从与目标视频不对齐的条件中学习。我们提出 SolarRenderer，一个结构条件的视频渲染器，用两个轻量 LoRA 适配冻结的 MiniMax-H3 33B 骨干。结构视频在其所描述帧的位置进入骨干原生的参考通路，不带类型标识，只用普通文字描述，从而单个控制 LoRA 就能跟随任意结构表示。从一个预训练的四步 LoRA 出发，结构引导的分布匹配让模型四步完成渲染，比 50 步采样快 12.3 倍，同时保留学到的控制能力。一个块因果变体把同样的设计扩展到流式场景，可实时渲染 768p 视频。为训练模型，我们从游戏引擎、仿真器和 YouTube 视频构建了一个 13.6 万段的帧对齐语料。在分布内测试集和覆盖 16 种结构表示的泛化基准上的实验表明，SolarRenderer 在两者上都达到最先进水平，并能泛化到 11 种未见过的表示，包括姿态骨架、手绘图和点云。
