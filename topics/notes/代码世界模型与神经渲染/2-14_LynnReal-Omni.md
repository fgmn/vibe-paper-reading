## 一句话总结

在 **MiniMax-H3 架构**上做的"一个模型干所有视频活"：32B 的共享多模态 DiT（50 块、宽 5,376）把文生视频、首帧 / 首尾帧、多主体参考、人体与手部姿态控制、游戏录像 / 网格渲染视频控制、视频编辑、逐帧修复、分块长视频都装进**同一组权重**，靠每个 token 带上**模态标签、行索引、3D RoPE 坐标、逐行噪声时间**来区分角色；逐帧对齐的控制视频和目标共享空间网格，但时间坐标**故意错开一个常数 Δ>0**。训练时把 caption 引导"拟合"进模型（w=3，推理不再跑无条件分支），再用低秩 TDM + Reward Forcing 蒸馏到 **4 步**；另训一个 **27B Flash**（保留 42/50 块、中间 26 块空间 token 只留约 1/4、3 步）和一个 36→26 块的**轻量 VAE 解码器**。单张 H100、540p 22 帧，热启动 DiT+解码 **843 ms（Standard）/ 377 ms（Flash）**；768p 5 秒片段则要 20.0 s / 7.2 s。长视频按 17 帧一块续写，历史压成不超过 2 个全分辨率潜帧的 token 量（首帧全分辨率 + 最近 2 帧步长 2 + 更早至多 8 帧步长 4）。自建的多镜头音视频基准 MSAVP 上总分 T2V 77.76、I2V 79.20，比 50 步的 MiniMax-H3 低约 1.5 分。"代码世界 + 渲染器"这条线上，它是第三方评测里的强基线（WorldDraft 总分第一、SolarRenderer 泛化 Elo 并列第一），但**本文自己对结构控制 / 游戏渲染没有任何定量评测**。

## 要解决什么问题

作者的出发点是"智能体做视觉创作"（[[topics/papers/代码世界模型与神经渲染/2-14_2609.15863_LynnReal-Omni.pdf#page=3|图 1，第 3 页]]）：智能体能写参考图、搭可编辑的 3D 场景、写带碰撞规则的可执行小游戏，把几何和运动显式化；但只靠这些，画面里的物体和角色不够精细。所以要把"智能体给的显式控制"和"视频扩散给的外观"合起来。要做到这一点，现有方案有四个缺口（第 3 页 §1）：

1. **任务管线割裂**：文生视频、视频到视频、参考生成、结构控制、编辑、长视频各有各的模型，智能体得拼多个模型和临时接口，行为也不一致。
2. **长视频不一致**：外观漂移、身份变化、光度伪影。
3. **评测不完整**：VBench、VideoPhy 等不在一个协议里同时覆盖多镜头连续性、动作绑定、物理合理性、可控性和音频，而且不同量纲的指标被直接平均。
4. **解码成瓶颈**：少步蒸馏后去噪很便宜，VAE 解码反而成了主要开销；但解码器加速必须和去噪一起评，因为它会影响时间相位和重建质量。

## 方法

总览见 [[topics/papers/代码世界模型与神经渲染/2-14_2609.15863_LynnReal-Omni.pdf#page=9|图 3，第 9 页]]：(a) 各任务的 token 排布，(b) 共享 DiT 与控制的时间偏移，(c) 视频 / 音频两套噪声时钟下的 4 步，(d) 带共享边界帧的续写。

| 项目 | 内容 |
|---|---|
| 世界状态由谁维护 | 不在模型里：由智能体写的 3D 场景 / 可执行游戏维护（§4.7），模型只接收它们渲出的视频；本文没有交互闭环实验 |
| 条件信号 | 文字（三段或六段格式）、参考图、参考视频、首 / 尾关键帧、姿态序列（身体 + 手）、深度序列、游戏录像、网格渲染视频、编辑源视频、续写历史 |
| 骨干 | 32B 共享多模态 DiT，按 MiniMax-H3 架构（直接在 H3 上做，§2.1）：50 块、残差宽 5,376、56 头 × 128 维、FFN 14,336；视频潜变量 24 通道、1×2×2 patch；音频流 32 通道；文本条件 5,120 维（第 8 页 §4.2） |
| 条件注入 | 全部拼进一条序列做联合注意力；每行带模态标签、模态内行索引、3D RoPE、逐行噪声时间。没有 ControlNet 或通道拼接 |
| 输出 | 一次前向同时预测视频和（有的话）音频速度 |
| 推理步数 | Standard 4 次前向；Flash 3 次前向；长视频每块 4 次（README：默认 30 秒时第 8 块起每块 4+2） |
| 速度（H100，热启动） | 540p 22 帧：DiT+解码 0.843 s / 0.377 s；768p 5 s：20.0 s / 7.2 s（表 7） |

### 原生任务表示与"错开的"控制时间轴（§4.2）

- 每个任务把文本、参考、目标视频、音频按固定顺序打包，每行带四样东西：**模态标识、模态内行索引、3D 旋转位置、逐行噪声时间**。参考行和目标行因此即使在同一序列里也不会混淆角色。
- **图像条件有两条接口**：统一参考排布（图片作为有序的"图片参考段"，"开头帧是这张图"只是语义要求）；原生关键帧排布（首帧和可选尾帧编进目标的关键帧分区）。用哪条由权重包里的条件约定决定，Standard 和 Flash 都支持关键帧排布。
- **两类视频条件**：
  - *语义参考视频*：可以保留自己的分辨率，只提供外观或运动线索；
  - *逐帧对齐的控制*（姿态序列、编辑源、深度序列、游戏渲染）：按 24 fps 模型时钟重采样、缩放到目标画布，短了用最后一帧补齐。和目标**潜变量几何相同、空间网格相同**，时间位置满足 τ_target − τ_control = Δ（常数，Δ>0，式 1，第 9 页）。
- 作者特意强调：正的偏移让参考 token 和生成 token 留在不同的"域"里，**把两者的绝对 RoPE 坐标设成相等会改变模型对条件的理解**。这和 [[topics/notes/代码世界模型与神经渲染/2-09_SolarRenderer|SolarRenderer]] 的做法正好相反（后者让结构潜帧直接用目标帧的 RoPE 位置），两篇都基于 H3，值得对照。
- 论文**没写 Δ 取多少**，也没有消融 Δ=0 和 Δ>0 的差别，只是陈述。

### 多任务训练与少步蒸馏（§4.3）

- **目标**：clean-time 约定 z_t = t·z + (1−t)·ε，速度目标 v* = z − ε，只在有效目标行上算损失；条件行和补齐行不算。
- **噪声采样**：视频噪声水平用平移的 logistic-normal（s_v = 3u/(1+2u)，u = sigmoid(g)）；音频噪声由同一个 g 经过一个对齐的映射得到，但用独立的高斯噪声。损失 = 视频 MSE + 0.1 × 音频 MSE（只在有真实音频时），**缺音频不当成静音监督**。
- **引导拟合**（式 6）：同一个去噪器给出去掉 caption、stop-gradient 的预测 v∅（视觉控制保留），训练时用 v = (v_c + (w−1)·sg(v∅))/w，w=3。最优时 v_c ≈ w·v* − (w−1)·v∅，相当于把 CFG 学进条件分支，推理时**不加无条件前向**。[[topics/notes/代码世界模型与神经渲染/1-12_StreamRender-H3|StreamRender-H3]] 把这一招扩展成 caption + 结构两级。
- **Standard 的 4 步蒸馏**：低秩的轨迹分布匹配（TDM），四个不重叠的转移区间，每次只对学生的一个转移求导；冻结的老师 + 单独训练的全深度 fake-score 评委；视频项再按 Reward Forcing 的动态奖励加权（奖励模型不懂音频，所以音频项权重固定）。部署用学生的 EMA。
- 768p 下四步的 clean-time 时间点：视频约 (0, 0.0270, 0.0769, 0.2)，音频 (0, 0.1, 0.25, 0.5)；第四步更新后直接到干净端点，不需要第五次前向。
- **缺的东西**：多任务训练和蒸馏都**没有给数据量、步数、算力、各任务采样比例**。只说视频编辑数据"大规模"、明显提高了文字指令跟随（§3.7）。

### Flash 变体（§4.3.1）

| 项目 | 内容 |
|---|---|
| 深度 | 保留 50 块中的 42 块（约 27B） |
| token 压缩 | 前 2 块全序列 → 中间 26 块每帧空间步长 2 下采样视频 token（保留边界行列，约剩 1/4；文本、音频不压）→ 最后 14 块全分辨率 |
| 恢复 | H_out = H + U(F_mid(PH) − PH)：被丢掉的 token 拿最近保留 token 的特征增量（式 7） |
| 蒸馏 | TDM，3 步；冻结全深度老师 + 可训全深度 fake-score；生成器损失是归一化的伪 Huber（式 8，c=10⁻³）；另加真实数据 flow 回归和音频区间监督 |
| 量化 | §4.3.1 写的是 **W4A8**（INT4 权重 + FP8 激活）；但 §5.4、表 6、表 8 和 HF 模型卡都说 Flash 是 **INT8 权重 + INT8 激活（W8A8）**。需核对 |
| 支持的任务 | 论文和 Flash 模型卡都说只做**文生视频和原生首尾关键帧**；README 的 ComfyUI 额外给了 Flash 的参考图生视频（ref2v）工作流。**结构控制 / 游戏渲染没有 Flash 版** |
| 消融 | 同一 Flash 权重关掉 token 压缩（不重训），DiT 时间 263 → 453 ms（第 23 页） |

### 长视频：固定头重叠 + 有界历史（§4.4）

- **分块**：每块生成 17 个新帧。上一块最后一帧 RGB 重新编码成"共享边界"潜帧，固定不动；模型预测 5 个未来潜帧，和边界潜帧一起解码成 18 帧，再丢掉重复的边界帧。每块 4 次前向，没有插帧和曝光校正。
- **紧凑的时间上下文**：最早的一个潜帧全分辨率（相当于 sink）、最近 2 个潜帧空间步长 2、更早的至多 8 个潜帧步长 4；共享边界帧不重复放。token 总量 ≤ 2 个全分辨率潜帧（1 + 2×¼ + 8×1/16 = 2，算得上），所以注意力成本和视频长度无关。存储也有上界：满了以后保留首帧和最近几帧，丢中间。
- [[topics/notes/代码世界模型与神经渲染/1-12_StreamRender-H3|StreamRender-H3]] 的"sink + 近期历史"窗口就是沿用这一设计。
- **只有设计，没有结果**：表 2 列了"续写：720 个新帧、43 块"这项研究，但正文没有任何漂移或一致性数字。需核对（可能在演示视频里）。

### 轻量解码器蒸馏（§4.5）

- 老师是 H3 的 36 块视频解码器（宽 2,048），学生保留其中 26 块（具体编号见式 9），每块用对应老师块初始化；**编码器、潜变量维度、时空缩放全不变**，可直接替换。
- 训练样本 60% 来自编码的真实数据、40% 来自生成模型产出的潜变量（后者没有像素真值，只学老师）；25% 概率给潜变量加 3% 相对高斯扰动；图像用一个专门的图像解码器当老师（重建 L1 更低时）。
- 损失（式 11）：老师重建 L1 + 5×L2、多尺度 / 梯度 / 高通 / 小波 / SSIM、patch 和 tile 边界损失（tile 边界权重最大，1.5）、时间一阶 / 二阶差分、时空相位、最后 3 块的特征 L1、DINOv2 感知损失、经冻结编码器的后验 KL 一致性（800 步后启用，每 8 步一次），有配对像素时再加 Charbonnier。默认权重见 [[topics/papers/代码世界模型与神经渲染/2-14_2609.15863_LynnReal-Omni.pdf#page=14|表 1，第 14 页]]。
- 效果：同条件下解码从 469 → 340 ms；时间差 MAE 在运动片段上和官方解码器几乎相同（0.006015 vs 0.006012），在黏土片段上略差（0.005816 vs 0.005926）（第 22 页 §5.3）。只给了两段视频 + 一张图的例子，没有成规模的重建基准数字。

### 生成视频的逐帧修复（§4.6）

- 把视频每帧当一次图像编辑独立修复（同一 seed），每帧 4 次前向；图像编辑内部其实生成一段短片再挑一帧。
- 例子：5 秒、120 帧的蜡烛视频，480 次前向；目测背景网格和亮斑少了很多，但帧间有亮度和形状抖动、偶有残留点、火苗高度变化变小。**各帧独立，没有跨帧一致性约束**，作者自己也说时间一致性是局限。没有真值、没有指标。

### 智能体搭 3D 场景和可执行游戏（§4.7）

- 智能体从参考图 + 任务描述搭可执行 3D 场景：几何、材质、物体变换、灯光、相机，加显式状态更新和控制输入；靠代码执行、渲染结果和迭代修改闭环（先整体视角和布局，再局部比例、材质和光照）。
- 游戏逻辑用显式状态（位置、速度、朝向、动作阶段）+ 控制输入（移动、转向、动作触发），更新规则含加速度、重力、着地、碰撞；录制脚本按固定输出时间间隔推进仿真、每帧渲完再截，状态和事件跟帧一起存。这段录像作为布局和运动参考送进视频模型。
- 这部分**完全是流程描述**：用的是哪个智能体、哪个引擎、做了多少个场景 / 游戏，都没写。结果只有附图（[[topics/papers/代码世界模型与神经渲染/2-14_2609.15863_LynnReal-Omni.pdf#page=27|图 10–11，第 27 页]]）：一段游戏录像 + 本地改过的首帧（动漫风滑板），一段已有网格的环绕镜头渲成黏土风；图 1 的截图也注明"扩散输出未展示"。

### 数据管线（§3）

| 阶段 | 做法 |
|---|---|
| 来源 | 公开视频；内容约：剧情 / 动作 41%、体育 / 舞蹈 19%、动画 / CG 12%、自然 / 航拍 11%、日常 / 机械 9%、商业 / 其他 8%（图 2，按采集类别和筛选标签估计） |
| 预处理 | TransNetV2 低阈值 0.1 找切点，再用颜色、亮度、白像素比、边缘结构排除闪光、抖动、快速摇镜；PP-OCR 找广告、水印、字幕；最小裁剪，裁掉 >25% 的不裁 |
| 粗标注 | Qwen3.5-122B-A10B 看 48 镜头的拼图窗口（相邻重叠 12）分场景，再在 ≤8 帧的局部窗口里修正；每镜头最多 6 个可复用主体，两阶段定位框，跨镜头靠脸、衣服、形状、颜色、材质链接 |
| 筛选 | Qwen v4 Flash 快速筛故事和运动，Qwen3.5-122B-A10B 看全片复审；光流等统计只排序不决定；去重 |
| 资产 | 主体 / 背景参考（Big-LaMA 补背景）；Detectron2 + ViTDet 检测和跟踪人、全身姿态（含手）；MOSS-Transcribe-Diarize 0.9B 转写和说话人分离，Qwen3-Omni-Thinking 识别环境声、接触声、音乐 |
| 最终 | 每段 ≤60 s、同场景多镜头，带主体定义、总述、分镜头描述、音景、背景音乐和资产链接；自动检查编号、切点、框、主体引用等 |
| 规模 | 只说最终保留约 **原始存储量的 0.6%**；片段数、时长都没给 |

注意数据里**没有游戏引擎或仿真器的配对数据**：结构控制用的对齐条件来自真实视频上估出来的姿态（文中还提到深度序列，但没说深度怎么来）。游戏录像 / 网格渲染能当控制输入，靠的是"对齐控制"这条通用接口的泛化。需核对。

### 推理延迟（§5.4）

单张 H100 80GB，两次预热 + 五次计时，再在第二张卡上重复，取 10 次中位数；不含条件编码、加载、文件编码。

**逐项加速**（[[topics/papers/代码世界模型与神经渲染/2-14_2609.15863_LynnReal-Omni.pdf#page=24|表 6，第 24 页]]，540p 22 帧，单位 ms / GiB）：

| 累加的改动 | Std DiT+解码 | Std 生成墙钟 | Std 显存 | Flash DiT+解码 | Flash 生成墙钟 | Flash 显存 |
|---|---|---|---|---|---|---|
| 基线 | 2345 | 2682 | 77.2 | 1592 | 1920 | 52.4 |
| + QKV 拼接 | 2355 | 2684 | 77.2 | — | — | — |
| + W8A8 投影 | 3292 | 3627 | 59.9 | — | — | — |
| + 算子融合 | 1719 | 2045 | 59.9 | 976 | 1309 | 52.4 |
| + 自动调优 Triton INT8 GEMM | 1432 | 1767 | 59.9 | 869 | 1206 | 52.4 |
| + FlashAttention 3 | 1300 | 1633 | 59.9 | 823 | 1155 | 52.4 |
| + 时间调制缓存 | 1266 | 1600 | 60.0 | 801 | 1140 | 52.5 |
| + GPU 上转 RGB | 1268 | 1370 | 60.0 | 801 | 903 | 52.5 |
| + 轻量解码器（原生 tile） | 1081 | 1175 | 54.9 | 599 | 679 | 47.4 |
| + 自适应 tile | 935 | 1029 | 53.9 | 460 | 557 | 46.4 |
| + 解码器编译 | **843** | **959** | 53.9 | **377** | **479** | 46.4 |

- 没融合的 INT8 反而让 Standard 变慢（2355 → 3292），融合后才回本；算子融合省 43.6%（Standard）/ 31.6%（Flash）。
- 量化、融合、换注意力、换解码器都会改变数值输出，作者明说"延迟收益不等于画质等价"，但**没有给加速后的画质对比数字**。

**分辨率和时长**（表 7，第 24 页，单位 s / GiB）：

| 输出 | 模型 | 步 | DiT | 解码 | DiT+解码 | 生成墙钟 | 峰值显存 |
|---|---|---|---|---|---|---|---|
| 540p 22 帧 | Standard | 4 | 0.724 | 0.119 | 0.843 | 0.959 | 53.9 |
| 540p 22 帧 | Flash | 3 | 0.262 | 0.115 | 0.377 | 0.479 | 46.4 |
| 768p 5 s | Standard | 4 | 18.293 | 1.723 | 20.018 | 20.514 | 58.0 |
| 768p 5 s | Flash | 3 | 5.474 | 1.724 | 7.198 | 7.661 | 49.9 |
| 768p 10 s | Standard | 4 | 56.969 | 3.428 | 60.393 | 61.490 | 63.0 |
| 768p 10 s | Flash | 3 | 16.322 | 3.394 | 19.716 | 20.763 | 54.4 |
| 768p 15 s | Standard | 4 | 116.207 | 5.112 | 121.315 | 122.920 | 68.1 |
| 768p 15 s | Flash | 3 | 33.505 | 5.163 | 38.665 | 40.362 | 58.9 |

- 换算一下：540p 22 帧是 0.92 秒视频，Flash 0.48 s 生成，**吞吐上约 1.9 倍实时**；768p 5 秒（120 帧）Flash 要 7.66 s，**约 0.65 倍实时**，Standard 只有约 0.24 倍。整段一次生成时注意力随长度超线性增长（10 s 是 5 s 的约 3 倍）。

### 硬件

- 实际验证过的只有 **H100 80GB** 和一张 **48GB 显存的 RTX 4090**；A100、RTX 50 系、B200 只做了兼容性选择、没实测；作者明说 **24GB 的普通 4090 不等于测过的 48GB 卡**。
- 注意力按 FA3（Hopper，CUDA ≥ 12.3）→ FA2 → cuDNN SDPA → PyTorch Flash SDPA → 原生 SDPA 的顺序在新进程里探测并做数值校验；FA3 钉在固定 commit、需要时从源码编译。
- 显存低于 64 GiB 时 Flash 启动脚本逐 tile 解码；但这**不能让 Standard 塞进同样的显存**。
- 冷启动 prompt 时文本编码器只保留 H3 实际用到的 50 层，必要时整层经 CPU 中转（为了 48GB 4090 不爆显存）。

### 提示词格式（`skill/lynnreal-prompt/SKILL.md`）

- **先确认条件约定**：读权重包里的 `inference_config.json` 和推理参数，任务名本身不够。
- **三段式**（Standard / Flash 文生视频，原生首尾帧 I2V）：`integrated_multimodal_description`（`[Shot 1] ...`）、`overall_soundscape`、`non_diegetic_music`。用原生关键帧时，前面加"Picture 1 在 0.00 秒完全参考"的说明，两张关键帧要分别说明开头 / 结尾角色。
- **六段式**（图像参考、参考视频、姿态 / 网格 / 游戏渲染、视频编辑、图像编辑）：`subject_definitions`（`<Picture 1>`、`<Video 1>`……图片和视频各自从 1 编号）、`summary`（带任务前缀，如 `[reference generation]`、`[video editing]`、`[keyframe completion]`）、`retention_analysis`（每个参考标 `fully_preserved` / `partially_preserved` / `attribute_transfer` / `weak_reference`）、`detailed_description`、`overall_soundscape`、`non_diegetic_music`。这就是 H3 原生的六段格式，[[topics/notes/代码世界模型与神经渲染/2-09_SolarRenderer|SolarRenderer]]、AnyGameRenderer 也沿用。
- 写法要点：英文描述，台词 / 歌词 / 可见文字保留原语言；动作要和时长匹配（22 帧约 0.92 s，124 帧约 5.17 s）；对齐控制只描述实际采样到的时间窗；游戏 / 姿态控制要说清控制提供什么、风格图提供什么，**不要要求和对齐渲染相矛盾的相机路径**，骨架颜色、线框、代理材质只在需要时出现；网格渲染时让源视频决定每一时刻的视角，外观图只提供材质。
- 流式续写的 caption 写的是**下一段 17 帧（0.708 秒）的增量动作**，不是整段故事；sink 定外观和场景身份，不是"回到开头姿势"的命令。
- 没有独立的负向提示输入；当前流式版本**不生成音频**，声音字段写了也不会出声。
- 作者自己标注：这些写法建议是"假设"，要靠成对采样验证。

## 摘要（中文）

视频扩散模型具有随机性、难以控制：要得到精确内容往往需要反复采样且不保证成功，长时场景在外观、交互和时间连贯性上会漂移。智能体式视觉创作能提供显式参考、可编辑的 3D 场景或可执行的游戏状态来稳定控制，但本身并不保证物体或角色的高保真。两者结合可以实现稳定、高质量的生成。为此我们提出 LynnReal-Omni，一个原生多模态视频生成框架，建立在 32B 共享多模态扩散 Transformer 上，把文生视频、图像条件生成、参考引导生成、结构控制、编辑、退化视频修复和长视频生成统一起来。它接受异构的视觉输入——外观参考、可编辑 3D 渲染和游戏录像——让智能体能在一个统一模型里组合视觉条件。我们还专门训练了一个 27B 的 Flash 共享多模态扩散 Transformer 用于实时渲染。我们搭建了一套系统的数据管线，涵盖视频清洗、主体关联、多模态标注和对齐控制构建，得到精选的多镜头音视频片段语料；并提出 MSAVP，一个 100 条提示、20 项指标的评测设计，把指令跟随、生成合理性、视觉质量、时间行为和音频协调分开评估。LynnReal-Omni-Flash 通过模型和解码加速（包括一个轻量 VAE 解码器）进一步降低推理成本：在一张 H100 上，热启动生成并解码一段 22 帧 540p 视频，LynnReal-Omni 需要 843 ms，Flash 需要 377 ms。这些结果为实时流式视频生成打下基础，使 LynnReal-Omni 成为面向智能体视觉创作的统一、可控、高效的基础模型。
