## 一句话总结

Matrix-Game 系列从"状态藏在视频里"的交互世界模型（2.0 / 3.0 / 3.5）转向"**代码管规则、引擎管状态、视频模型只画画**"：一个轻量游戏引擎维护世界状态并渲出**低模代理**（黑天、灰棋盘地面、纯色方块建筑、积木人、黑描边），一个多模态编码智能体按玩家的自然语言改游戏代码，渲染器是从 **Wan2.2-Fun-5B-Control** 改出来的因果 DiT：低模代理与噪声潜变量**按通道拼接**，引擎状态按模板生成的**动态字幕**走交叉注意力，再加按相机位姿检索的 3 张空间记忆帧和首帧。训练数据是 UE5 里四个场景、**1712 小时**、像素对齐的低模 / 高保真配对视频，每个游戏单独训一个模型；按 Causal Forcing++ 蒸馏成每块 1 个潜帧（4 帧）、1–2 步的自回归生成器，再叠 CUDA Graph、FP8、Triton 融合、环形 KV 缓存、split-KV 注意力、TAEHV 解码。结果：单张 **RTX 5090** 上 480p、1 步 **83.4 FPS**、峰值 18.2 GiB，**按键到画面 112 ms**（未优化时 1110 ms）；2 步 57 FPS。和 CWM、StreamRender-H3、AgentGarten、Magpie 相比延迟最低、且唯一跑在消费级单卡上（表 3）。代码、权重、低模游戏资产开源。画质只有定性图，没有任何定量指标。

## 要解决什么问题

作者认为，从"短暂探索"走向"规则丰富的长时游戏"时，靠视频生成维护世界状态的系统（Genie 系列、Matrix-Game 2.0 / 3.0 等）有四个问题（§1）：

1. **没有持续的外部纠正**：世界状态隐含在像素和上下文里，视野外的区域没有显式状态。
2. **误差累积**：自回归里小错不断放大；即使接外部 3D 工具，估计的相机位姿误差也会累积到场景崩塌。
3. **未压缩的逐帧记忆**：历史帧不合并成紧凑表示，记忆开销随 rollout 长度增长。
4. **玩法机制有限**：交互多是导航和简单环境响应，缺可执行规则、持久后果、可追求的目标。

更根本的观点：扩散模型学的是统计相关，画面逼真不代表懂因果或物理；作者借 Jakobson 的"符际翻译"说法，认为当前视频生成器的语义理解大多来自上游的多模态大模型或文本编码器，**扩散更像渲染器**。再加上实时低延迟、超越导航的玩法、多人共享状态这些需求，结论是：外部系统维护状态和规则，视频模型只做视觉渲染。

## 方法

### 三个角色（§2，[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=3|图 2，第 3 页]]）

| 角色 | 作者的比喻 | 做什么 |
|---|---|---|
| 游戏引擎 | 裁判（Referee） | 用简化几何表示道路、建筑、角色、可交互物体；血量、背包、重力、碰撞、任务进度等**在代码里显式维护和执行**；持续输出结构渲染（"场景草图"），约束布局、物体运动和视角；物体离开视野后状态仍由引擎维护 |
| 多模态编码智能体 | 编剧 + 翻译 | **上游**：把玩家想法写成游戏代码和场景配置（改地形、摆物体、改 NPC 行为、设计新机制），玩家没说细节时自己补（比如开门后编出"角落里有个上锁铁箱的储藏室"并注册进引擎，此后箱子状态由引擎管）；**下游**：把引擎的场景结构和事件结果翻译成文字描述（例如"射中油桶是否爆炸由引擎判定，智能体只描述爆炸的画面"） |
| 视频生成模型 | 画师（Painter） | 在保持结构和运动约束的前提下生成材质、光照、氛围和细节 |

实时循环：玩家输入 → 引擎更新状态 → 结构渲染 + 控制信号 → 实时视频渲染 → 画面反馈。

- 世界状态怎么"用代码表示"：游戏规则和状态就是引擎里的游戏代码（射击、驾驶两类游戏的代码随论文开源），编码智能体通过**编辑场景配置和游戏代码**来改规则。论文没有说明引擎具体是什么（"lightweight game engine"），也没写编码智能体用的是哪个模型（需核对仓库）。
- 注意：训练数据来自 **UE5**，但运行时的"轻量引擎"是否就是 UE5，正文没写清（需核对）。

### 数据：UE5 低模 / 高保真配对（§3.1，[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=6|表 1，第 6 页]]）

| 场景 | 游戏类型 | 训练片段 | 小时 | FPS | 留出 |
|---|---|---|---|---|---|
| 中世纪城堡 | 第三人称射击 | 17,848 | 290 | 24 | 3 个采集会话，683 段 |
| 古埃及沙漠 | 第三人称射击 | 40,296 | 643 | 24 | 3 个采集会话，617 段 |
| 沙漠峡谷空战 | 飞行战斗 | 28,720 | 467 | 24 | 整批多机采集 |
| CitySample 大城市 | 驾驶 | 27,470 | 312 | **17** | 3 个采集会话 |
| 合计 | | **114,334** | **1,712** | | |

- 每次采集 1280×720，包含**三路对齐视频**：UE5 RGB 渲染、低模结构渲染、代理几何的深度渲染，外加逐帧元数据。射击和空战片段约 1 分钟。留出会话 / 批次不贡献任何训练片段。
- 两路渲染相机轨迹、时间戳严格同步，同一帧号的低模帧和高保真帧**逐像素对齐**（[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=5|图 3，第 5 页]]）。
- 低模代理的样子：建筑、地形、植被、动态物体经自适应几何拟合和视锥剔除，去掉反射、高频纹理、复杂光照；天空是黑的，地面是灰棋盘格，建筑和墙是纯色方块 / 棱柱，树是圆柱 + 球，角色是积木人，所有图元黑描边、无纹理无反射无阴影。
- 同时记录物体实例 ID、可见性、因果交互事件，形成每段的语义元数据流。

### 动态字幕（§3.2，[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=7|图 4，第 7 页]]）

- 每个物体有 ID，关联一条语义描述（例：City 1247 → 现代四门轿车；Egypt 95 → 大石头金字塔）。
- 系统从引擎读当前可见物体和实时状态，填进模板生成当前帧的描述：视角、方向、距离、可见性变化、物体运动、按帧号的玩法事件（"第 18 帧发生车辆碰撞"）。
- 图 4 的例子标明是**基于规则、不用视觉语言模型**：停着的车离开视野就从描述里消失，行人从"站着"变成"走近"，新出现的物体写在"Changes"下面。
- 分工：**代理给结构**（位置、布局、运动），**字幕给语义**（画面里有什么、各自什么状态）。

### 渲染器架构（§4.1，[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=8|图 5，第 8 页]]）

| 项目 | 设置 |
|---|---|
| 起点 | Wan2.2 5B 的 **Fun Control** 变体（Wan2.2-Fun-5B-Control），改成视频到视频（V2V） |
| 规模 | DiT 5B 参数，30 个块，宽 3072，FFN 隐层 14336 |
| 低模代理 | 用 TAEHV 编码后，与噪声潜变量**按通道拼接**：48（噪声）+ 48（代理控制）+ 52（全零）= 148 通道 |
| Patch 嵌入 | 1×2×2 3D 卷积，480×864 下每个潜帧 15×27 = **405 个 token** |
| 注意力 | 因果自注意力 24 头 × 128 维，QK-Norm；3D RoPE 给时间 / 高 / 宽分配 44 / 42 / 42 维 |
| 动态字幕 | umT5-xxl 编码，交叉注意力；字幕的 K/V 缓存，**只在字幕变化时重算** |
| 时间步 | 正弦编码 → MLP，经 AdaLN 调制每个块 |
| 输出 | LayerNorm + 线性 + unpatchify 预测速度，z ← z − σv 走 1 或 2 步；TAEHV 解码 4 帧 |
| 自注意力 KV 缓存 | 3 个空间记忆帧 + 参考帧（首帧）+ 最近 20 块 |
| 写缓存 | 一块生成完后，在 t = 0、**去掉控制输入**的条件下再跑一次，把干净的 K/V 写进缓存，后续块看的是干净历史 |

四类条件各司其职：低模代理（画什么、画在哪）、动态字幕（细节和当前事件）、空间记忆参考帧（回到同一地点时保持一致）、首帧（接上屏幕上已有的画面）。

### 训练三阶段 + SFT（§4.2–4.3）

| 阶段 | 做什么 | 分辨率 / 窗口 | 关键超参 |
|---|---|---|---|
| SFT（每个游戏一个模型） | 从 Wan2.2-Fun-5B-Control 出发，按 Wan 的 flow matching 做**双向** V2V 微调；条件 = 低模代理 + 字幕 + 首帧 + 最多 3 个上下文帧（空间记忆） | 704×1280，81 帧窗口 | 64 卡，全局 batch 64，AdamW，lr 1e-5，4,000 步；首帧丢弃概率 0.3、字幕 0.2、代理 0.2（为 CFG 和无首帧生成） |
| 1：teacher forcing 自回归扩散 | 每个潜帧独立噪声级，只看之前的干净真值帧、首帧、上下文帧 → 得到多步 ODE 采样的因果教师 | 480×864，81 帧 | lr 2e-6，20,000 步 |
| 2：因果一致性蒸馏 | 冻结教师 + 在线学生 + EMA 学生；48 级噪声网格上教师带 CFG 3 走一步 Euler，在线学生对齐 EMA 学生的预测 → EMA 学生 4 步出一块 | 同上 | 5,000 步，EMA 0.99 |
| 3：分布匹配（非对称 DMD） | 学生在自己的自回归 rollout 上学；real score = 冻结的双向模型（CFG 3），fake score 在线训练；学生每块 **2 步**，首个潜帧 4 步 | 同上 | fake score 每步更新、学生每 5 步更新；lr 4e-7 / 2e-6；从阶段 2 末尾再训 1,000 步 |

- 上下文帧的选法（SFT）：从窗口之前至少 40 帧的历史里，留下视野与窗口重叠的候选，按相机位姿取最近的几帧；作为 t = 0 的干净潜变量放进序列，不算损失。
- 阶段 3 的"最新配方"为对齐部署设置加了三处：rollout 长度随机取 21 / 41 / 61 / 121 个潜帧，滚动缓存 = 首帧 + 最近 20 个潜帧，两个 score 只评最后 21 个；每个 20 帧段开头按位姿检索最多 3 个空间记忆帧加入缓存；部署时代理用 TAEHV 编码，所以学生 80% 的步数收 TAEHV 编码的控制、20% 收 Wan-VAE 编码，两个 score 始终看 Wan-VAE 编码。
- 每个游戏一个模型，四个场景就是四个渲染器。

### 实时推理（§5，[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=10|图 6，第 10 页]]）

块很短（4 帧）让响应快，但模型调用变得很频繁：1 步时每次调用算力很小，GPU 大量时间在等 CPU 发 kernel。逐项去掉开销：

- **发射开销**：DiT 主干录成 CUDA Graph 一次回放；线性层 FP8 权重。
- **融合 kernel**：Triton 写 RoPE、归一化、FP8 量化；Q/K/V 投影共享一次输入量化；字幕 K/V 缓存。
- **KV 缓存与注意力**：历史 KV 用**环形缓冲**，新潜帧覆盖最旧槽位，不搬数据；自注意力把 KV 窗口切成 7 段并行算，用 log-sum-exp 合并（split-KV / Flash-Decoding），每段的 INT8 K / FP8 V 缓存着，只重新量化变化的那段。
- **解码与 I/O**：完整 Wan VAE 解码器换成 TAEHV，输入输出异步流水线；图 6b 还把解码挪到"写干净 KV"之前，先出画面。
- 图 6a 的每块 GPU 时间：1 步 70.5 → 40.1 ms（kernel 数 6.5k → 2.9k），2 步 100.6 → 58.1 ms（9.5k → 4.0k）。

## 实验与关键数字

### 推理优化逐项累加（[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=11|表 2，第 11 页]]）

设置：480×864，每块 1 个潜帧（4 帧），KV 窗口 21 个潜帧，单张 RTX 5090。FPS 是模型稳态生成速率；延迟是从按键到第一帧反映它的画面，游戏以 60 FPS 运行。

| 配置 | FPS ↑ | 延迟（ms）↓ | 加速 |
|---|---|---|---|
| 因果 Wan2.2 DiT，4 步，完整 Wan VAE | 4.5 | 1110 | – |
| + 小 VAE（TAEHV） | 6.5 | 867 | 1.4× |
| + RoPE kernel、缓存字幕 KV | 15.4 | 551 | 2.4× |
| + 8 位权重 + CUDA Graph | 24.2 | 466 | 1.6× |
| + 1 步蒸馏 | 51.2 | 376 | 2.1× |
| + 异步 I/O 流水线 | 57.7 | 367 | 1.1× |
| + 融合 Triton kernel | 65.8 | 121 | 1.1× |
| + 环形 KV 缓存 | 73.7 | 117 | 1.1× |
| + split-KV FlashAttention | **83.4** | **112** | 1.1× |
| 总计 | 快 19× | 低 9.9× | |

- 1 步：一块 4 帧去噪 48 ms，约 83 FPS；2 步约 57 FPS；两种情况峰值显存都约 **18.2 GiB**。文本编码器、DiT、VAE 都在同一张卡上。
- 16 GiB 消费级卡（480×864、1 步、**固定提示词**）：RTX 5080 约 67 FPS / 12.8 GiB，RTX 5070 Ti 约 58 FPS / 10.9 GiB。

### 与同类系统对比（[[topics/papers/代码世界模型与神经渲染/1-11_2610.27999_Matrix-Game-4.0.pdf#page=12|表 3，第 12 页]]）

这是专题清单"实时性对比"表的来源，逐格对照如下（开源状态是作者 2026-10-19 查各项目 GitHub / Hugging Face 得到的）：

| 系统 | 延迟 | 分辨率 | 硬件 | 开源 |
|---|---|---|---|---|
| Code World Model（流式）[25, 26] | ≈10.2 s | 1344×768 | 1× H200 141 GB；峰值显存 108–123 GB，80 GB 卡放不下 | 代码和 LoRA 权重；40 个示例代理；代理生成器未开源 |
| StreamRender-H3 [27] | ≈517 ms | 1344×768 | 8× GB200，上下文并行 | 代码、权重、赛车引擎及赛道和车辆资产 |
| AgentGarten [28] | ≈878 ms | 832×480 | 1× H100 80 GB（数据中心卡） | 渲染器代码和权重；实时引擎和代码世界未开源 |
| Magpie [29] | ≈1.55 s | 1280×768 | 1× H100 80 GB（数据中心卡），峰值显存约 34 GB | Lite 版渲染 / 白盒视频数据集；代码和权重未开源 |
| **Matrix-Game 4.0** | **112 ms** | 864×480 | **1× RTX 5090**，32 GB 消费级单卡 | 代码和权重，发布即开源 |

表注里的口径（要点）：

- **分块系统的延迟 = 两次块生成时间**（纯生成时间，不含引擎和传输）：CWM 流式版 17 帧块 5.1 s（单张 H200）→ ≈10.2 s；AgentGarten 16 帧块 439 ms（单张 H100）→ ≈878 ms；StreamRender-H3 每块 258 ms，是其项目页三段时间之和——参考编码 16.67 ms + 两步渲染 217.96 ms + 因果视频解码 23.8 ms，**最后一项是在单张 GB200、720p 下测的** → ≈517 ms。
- **Magpie 例外**：用的是作者自报的端到端时间 0.83 s（引擎准备 20 帧）+ ≈0.1 s（传输编码）+ 0.62 s（渲染），不是"两块"。
- **Matrix-Game 4.0**：从按键到第一帧反映它的画面，游戏 60 FPS 运行。
- 正文说 Matrix-Game 4.0 的延迟"约为次优系统的五分之一"（112 / 517 ≈ 0.22），而且是唯一跑在消费级单卡上的。

- 图 7：三段 40 秒 rollout 在 1 / 11 / 21 / 31 秒的代理 vs 生成对照。作者描述：布局、相机、物体运动跟住代理；纯色方块变成石墙、茅屋、棕榈树、砂岩建筑、城市立面，积木人变成有纹理的角色，战斗出烟雾、火花、弹道；整段外观稳定，角色从头到尾保持外观。

## 局限 / 存疑

作者在 §8 写的后续方向：降推理成本和硬件要求（目标是在 Steam 上发技术预览）、提高画质、加高分辨率精修阶段、多人一致视角渲染、更精确的画面控制、扩展到更多游戏类型和场景。正文没有单独的"局限"一节。

读的时候值得核对的：

- **画质没有任何定量评测**：留出会话有逐像素对齐的高保真真值，却没报 PSNR / LPIPS / FVD，也没测结构贴合度（比如生成画面重估的布局 / 深度与代理的误差）、长时漂移，更没有消融（动态字幕、空间记忆、TAEHV 混合编码、t = 0 重写缓存各自的作用）。所有画质结论都来自图 7 的定性对照。
- **速度和画质用的不是同一个配置**：标题数字（83 FPS、112 ms）是 **1 步**；§6 的定性评测用的是 **2 步**（57 FPS）。1 步模型的画面长什么样，论文没单独展示。
- **1 步模型怎么来的没写**：§4.3 的阶段 3 训出的是"每块 2 步、首个潜帧 4 步"的学生，表 2 却有一行"+ 1 步蒸馏"；1 步模型的训练配方正文没交代（需核对仓库）。
- **表 2 的延迟跳变**：加"融合 Triton kernel"时 FPS 只涨 1.1×（57.7 → 65.8），延迟却从 367 ms 掉到 121 ms。图 6b 的"先解码、再写干净 KV"没有单独列成一行，很可能混在这一步里（需核对）。
- **"编码智能体写动态字幕"的说法前后不一**：摘要和 §2.2 说多模态编码智能体把引擎状态"翻译"成场景字幕；但 §3.2 和图 4 明确说训练和演示用的字幕是**基于规则的模板、不用视觉语言模型**。运行时字幕到底由谁生成、智能体"补全没定义的内容"后新物体的描述从哪来，需核对。
- **表 3 是"不同口径放在一起"**：其他分块系统是两次纯生成时间（不含引擎、传输），Magpie 是端到端，Matrix-Game 4.0 是含引擎的按键到画面；分辨率也不同（Matrix-Game 是 480p，其余多是 768p）；StreamRender-H3 的 258 ms 里解码一项还是另一张卡、另一个分辨率下测的。"五分之一"的结论方向没问题，但不是同条件对比。
- **"60 FPS gameplay"**：游戏逻辑以 60 FPS 运行，渲染器 1 步时生成 83 FPS，渲染出来的画面怎么和 60 FPS 显示对齐（丢帧还是限速）没说。
- **每个游戏一个模型、只有四个场景**：智能体可以改规则、加机制，但视觉上能否画出训练场景之外的新物体 / 新场景（例如智能体"想象"出的储藏室）没有实验；换新游戏就要在 UE5 里重新采几百小时配对数据并重训。
- **评测时长与帧率**：961 帧按 24 FPS 是 40 秒，但城市驾驶数据是 17 FPS 采的，这一段实际对应约 56 秒的游戏时间（需核对评测时是否重采样）。空战场景在图 1 里有留出示例，但 §6 的评测没包括它。
- **记录了但没用的深度**：每次采集都有代理几何的深度渲染，架构里却只用低模 RGB 代理，深度没进模型。
- **字幕的空间信息很粗**：模板只有"左 / 右 / 上 / 中、约多少米"，小物体或密集场景下能否对上号没评。
- **每块要多算一遍**：生成完后要在 t = 0、无控制条件下重跑一次写 KV（图 6b 里的"clean KV"一段），论文没单独报这一遍的耗时，也没讨论去掉它的影响。
- **注意力 kernel 的叫法不一**：正文和表 2 写"split-KV FlashAttention"，图 6a 的标注却是"split-range Sage"（19.0 → 9.4 ms）、图 6d 写 INT8 K / FP8 V，看起来实际用的是 SageAttention 式的量化注意力（需核对代码）。

## 摘要（中文）

从可控视频走向真正可玩的世界，需要持久的世界状态、可执行的游戏规则和低延迟交互。我们给出下一代 Matrix-Game 的路线图：通过可执行的游戏外壳（harness）把游戏执行和视觉生成分开，并推出基于这一设计的第一个系统 Matrix-Game 4.0。轻量游戏引擎维护世界状态、执行交互规则；多模态编码智能体把玩家的想法翻译成游戏代码和动态场景字幕；基于自回归视频模型的渲染器在动态字幕和记忆参考的条件下，把引擎渲出的低模代理转换成细致的画面。这一框架为视觉生成提供持续引导，并支持用自然语言创建和修改场景与玩法。渲染器在对齐的低模与高保真视频对上训练，并蒸馏成按四帧一块、每块一到两步去噪生成的因果生成器。配合针对性的推理优化，Matrix-Game 4.0 在单张 NVIDIA RTX 5090 上实现 480p、60 FPS 的游戏体验，按键到显示延迟 112 ms。单步生成的稳态吞吐达 83 FPS，峰值显存 18.2 GiB；在固定提示词下，RTX 5080 上稳态吞吐也能到 67 FPS，RTX 5070 Ti 上 58 FPS。我们演示了由引擎保证机制的可定制射击和驾驶游戏，并开源代码、模型权重和低模游戏资产，以支持可玩游戏世界的研究和创作。
