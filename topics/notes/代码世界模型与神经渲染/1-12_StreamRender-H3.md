## 一句话总结

把交互世界拆成两半：**Three.js 写的浏览器赛车游戏**管地图、物理、规则和相机，每帧只导出一张**语义图**（13 类，每类一个平色，无光照纹理）；**MiniMax-H3 Ref2VA** 改成的流式扩散渲染器把语义图当参考视频逐块生成逼真画面，外观完全由会话开头的一张参考图和一段 prompt 决定，换参考图就能换天气和画风。渲染器经过 teacher forcing → Resampling Forcing（同时把 caption 和结构两级 CFG"拟合"进模型，单次前向）→ 流式 DMD 三阶段训练，部署时每块 2 步去噪；在 8 张 GB200 上，经过静态上下文 KV 缓存等五项优化，每个流式步的扩散渲染从 799.66 ms 降到 217.96 ms（3.67×）。H3 原版 VAE 解码器由 Claude Code 跑"提议–实现–测量"循环改造成 24 层的严格因果解码器，再用 KDA 内核智能体融合算子，720p 下 2 个潜帧 23.8 ms（原版 326 ms，13.7×），PSNR 33.04 dB（TAE 27.11 dB）。

## 要解决什么问题

- **世界逻辑要显式可控**（"Why Separate World Logic from Visual Generation"）：道路位置要能查询，碰撞要按可执行规则走，回到同一地点地图要一样。代码天然能做到，还方便改规则、调试、复现交互。
- **画面可以交给视频模型**：视频模型能用参考条件给同一结构和运动换不同外观，不必再走传统 3D 渲染管线出最终画面。
- **和 DLSS 5 的区别**：页面把 NVIDIA DLSS 5 列为先驱——它拿每帧渲染的颜色和运动矢量加上逼真的光照和材质，外观仍锚定在原 3D 内容上。StreamRender-H3 往前一步：引擎**只给语义图**，每帧的全部外观都由模型生成，换参考图和 prompt 可以彻底改变外观。
- **交互和离线生成的两点不同**（§2.3）：视频不能提前生成（内容取决于玩家还没给的输入）；每个输入要足够快地出现在屏幕上。所以引擎和渲染器要在同一条流上同时工作。

## 方法

### 整体结构（§2，"Overall Architecture"）

| 部分 | 内容 |
|---|---|
| 代码游戏引擎（§2.1） | three.js 浏览器赛车游戏（来自 `yitongl/CodeGameEngine`，保留 TORCS 源码声明和 Free Art License 资产）。维护三类信息：**地图**（几何、布局、物体及其类别）、**物理与规则**（固定时间步，同样输入序列必得同样轨迹，可复现；训练录制里每辆车都由 AI 司机驾驶）、**交互反馈**（每步读输入、推进世界、报告物体位置和相机朝向，再从相机视角画出当前状态——这张图不必好看，只需准确表达结构） |
| 中间表示（§2.2） | **语义图**：每个像素按所属物体类别涂一种平色，无光照、纹理、阴影。赛车 demo 13 类：道路、路肩、地形、草地、植被、岩石、护栏、建筑、看台、广告牌、天空、玩家车、对手车；类别和颜色在训练和部署间固定共享。作者认为深度图、边缘图、游戏自身的低保真渲染也"在一定程度上"满足要求，选语义图是因为它恰好包含世界逻辑决定的量（布局、轮廓、位置、运动、相机）而完全不含外观，且任何能按类平涂的引擎都能驱动 |
| 渲染器 | MiniMax-H3 Ref2VA（由 prompt + 参考图 + 参考视频生成视频和音频）。语义流作为**参考视频**输入，每个潜帧与同一时刻的输出潜帧对齐，所以语义视频决定每一帧的结构 |
| 接口 | 引擎和渲染器只共享语义帧流和会话的外观条件，两边都能单独替换；换一个游戏只需输出同格式的语义帧 |

### 交互循环（§2.3）

- **会话初始化（只做一次）**：引擎画开场帧 → 图像生成模型把它重绘成逼真参考图 → 参考图和 prompt 编码一次，整个会话保留。README 说明部署时参考图是**离线准备的资产**，交互循环里不需要调用图像生成 API；prompt 和首张参考图由 Qwen（README 致谢里是 Qwen3-VL）编码一次。
- **循环（不停顿，每轮五步）**：玩家键盘 / 手柄输入 → 引擎在下一个物理步应用并推进世界 → 引擎每个视频帧画一张语义帧并流给渲染器 → 渲染器凑齐一块的语义帧，用几步去噪（demo 中 2 步）生成，条件是会话外观和自己最近的输出，再解码成 RGB → 显示，玩家在下一轮反应。
- **实时条件**：每一块在上一块播完之前就绪。
- 部署规格（README "Runtime profile"）：引擎输入 1344×768 RGB 语义帧、24 fps；参考编码 832×480（最近邻缩放保留类别颜色）；输出 1344×768；没有固定的视频总时长。每个 worker 分配只支持一个活跃会话。

### 外观控制：参考图 + prompt（§3.1.1）

- 只给 prompt 太粗，几句话定不住具体材质、配色、光照，所以加一张**与开场语义帧对齐的参考图**：保留构图、相机、布局和每个物体位置，自由决定材质、车身涂装、天气、光照、风格。因为与第一张语义帧对齐，渲染器能知道哪种外观属于哪一类。
- **prompt** 用 MiniMax-H3 的结构化模板：定义主体（demo 里是玩家车、对手车、赛道及周边三个），说明每个主体的哪些属性由哪个输入控制（外观来自参考图；轮廓、位置、运动、相机来自语义视频），并写明语义视频里每种颜色代表哪一类，以及渲染风格、光照、声音。

### 训练数据（§3.1.1 "Training data in the racing scenario"）

| 项目 | 数值 |
|---|---|
| 配对片段 | 10,000 段，每段约 15 s |
| 来源 | 约 5,100 场录制比赛，39 条赛道（公路赛道、土路、椭圆赛道） |
| 车辆 | 全部由 AI 司机驾驶，每场 0–15 辆对手车；相机在玩家车后方跟随 |
| 录制 | 引擎的普通渲染 + 语义视频，1344×768、24 fps |
| 参考图 | 图像编辑模型 GPT-Image-2.5 把普通渲染的首帧重绘成"现代逼真赛车游戏截图"，保留相机、赛道、每辆车的位置大小、对手车颜色和玩家车涂装与编号；只在已有同类物体的区域加细节（如看台上的观众），不加车 |
| 光照风格 | 10 种轮流分配，每种 1,000 段：正午晴天、清晨阳光、黄金时刻、日落、蓝调时刻、阴天、碎云、夏日薄雾、晨雾、乌云透光 |
| prompt | LLM 智能体（Claude Opus 5.5）看普通渲染和语义视频，生成参考图请求，并为目标的每一段写一条 prompt，按时间戳叙述事件（何时入弯、何时超车） |
| 目标视频 | **原版 MiniMax-H3 Ref2VA** 用参考图 + 语义视频 + prompt、25 步去噪生成。原版能一次生成 15 s，但约 5 s 后就不再紧跟语义视频和参考图，所以每段拆成三个约 5 s 的子段，每段从上一段末帧续写 |
| DMD 阶段数据 | 不需要目标视频：同一批比赛里的 5,000 段 60 s 驾驶，各带语义视频、参考图、prompt |

也就是说，渲染器的预训练目标是 **H3 自己生成的视频**，不是真实视频；后面 DMD 的真实评委也是原版 H3。

### 流式窗口与时间一致性（§3.1.2）

- 沿用 **LynnReal-Omni** 的流式设计：每块和两种上下文放在同一个窗口里一起去噪——
  - **sink**：流的开头部分，整个会话都留在窗口里，锚定场景和物体身份（同 StreamingLLM 的 attention sink、LongLive 的 frame sink）；
  - **近期历史**：紧挨当前块之前生成的部分，把运动带过块边界。
- 窗口内注意力是**双向**的；第一个窗口之后的每个窗口都映射到同一个位置模板，所以流后期的窗口在生成器看来和早期窗口一样。

| 设置 | sink | 近期历史 | 当前块 | 备注 |
|---|---|---|---|---|
| 部署（demo） | 2 个调度单元 | 2 | 2 | 每个调度单元含 1 或 2 个潜帧；第一个窗口一次生成 7 个单元作为启动 |
| 预训练 | 4 | 5 | — | 更宽的窗口，窗口内稠密注意力 |
| DMD | 2 | 2 | 2 | 与部署相同 |

- **前缀缓存**：文本 / 图像条件、参考图、sink 在第一次续写后不再变化，于是把窗口拆成"固定前缀 + 移动部分"，前缀只看自己，移动部分看整个窗口。推理时前缀的 KV 每个去噪步算一次，之后每块复用，只重算近期历史和当前块。DMD 阶段用同样的注意力掩码并用当前权重重算前缀，保证训练和推理计算一致。

### 三阶段训练（§3.1.2–3.1.3）

| 阶段 | 历史从哪来 | 作用 |
|---|---|---|
| 1. Teacher forcing | 每段采一个窗口，历史取真值 | 普通多步扩散预训练 |
| 2. Resampling Forcing（+ 引导拟合） | 沿流训练：每个训练片段是一串连续窗口，每步处理每条流的一个窗口，输出写回作下一窗口的历史；写回的是**重采样过的真值** | 让生成器学会从含自身误差的上下文续写 |
| 3. 流式 DMD | 写回生成器**自己生成的块**，不用真值 | 蒸馏到每块 2 步 |

**Resampling Forcing 的借用方式**：原方法端到端训练因果自回归视频模型，用自重采样让模型在历史帧上见到自己的误差。这里窗口内是双向注意力，所以只借"重采样"这一步：每条流从移位 logit-normal 分布抽一个噪声水平，每个窗口把真值块加噪到这个水平、由生成器无梯度地重采样，写回的是重采样结果；当前块对真值训练。

**引导拟合（把 CFG 训练进模型）**：

- 发布的 MiniMax-H3 已做过引导蒸馏，每步一次前向；但要紧跟语义视频还需要对结构条件做引导，对 caption 和语义视频做 CFG 每步要三次前向。
- LynnReal-Omni 只对 caption 拟合一级引导；这里扩展成三支链：∅（无 caption、无语义视频）、T（加 caption）、TS（再加语义视频），参考图在每支都有。demo 的设定是 caption 一级放大 **1.5**，结构一级放大 **3.0**。
- 反推：把网络原始输出 f 当作已引导的预测，逐级缩回 u(∅) = f(∅)，u(T) = f(∅) + [f(T) − f(∅)]/1.5，u(TS) = u(T) + [f(TS) − f(T)]/3.0；每级起点加 stop-gradient，得到 u(T) = (2f(T) + sg f(∅))/3，u(TS) = (f(TS) + sg f(T) + sg f(∅))/3，再对每个 u 用普通扩散损失训练。收敛后单次调用 f(TS) 就等于引导后的预测。
- 把最强的引导放在加入语义视频这一级，使生成视频的布局、物体和相机与引擎状态一致。引导拟合和 Resampling Forcing 在同一次预训练里一起学。

**两步蒸馏与流式 DMD**（§3.1.3）：

- 预训练后的生成器每块要 **16 步**去噪，太慢。DMD 后每块两步：纯噪声 → 中间噪声水平 → 干净块。
- 沿流训练、无真值：每条训练流覆盖 60 s 驾驶的前 30 s。每步从生成器自己之前的输出生成每条流的当前窗口，只在这一块上算损失并写回；后面窗口的历史是由更早版本的生成器生成的，不回传梯度（同 Self Forcing 的"在自己的 rollout 上训练"和 LongLive 的流式长调优，但这里每步只推进一块而不是几秒）。
- **短跨度评委**：真、假评委都是原版双向 MiniMax-H3 Ref2VA，各自给 rollout 中以当前块结尾的一段连续跨度打分，跨度最多 **29 个潜帧（约 4 s）**；跨度起点那帧当参考图，同跨度的语义视频当参考视频。真评委就是发布的模型本身，冻结、无适配器；假评委从同一权重起加新 LoRA，在生成的跨度上用引导拟合（尺度 3.0 和 4.0）训练，用 u(TS) 打分。假评委在整段跨度上学习，生成器只通过当前块更新。
- **按时间线切 prompt**：评委看到的是长驾驶中不同的几秒，prompt 必须恰好描述那段。作者发现不带时间戳描述该段动作时，模型不知道参考图在时间线的哪个位置，**有时甚至把语义视频倒着渲染**；在 prompt 里描述玩家车外观能保住颜色。所以每段 60 s 驾驶用 GPT-6.1 Sol 智能体标一次时间线：输入语义视频、每 0.25 s 采样的两张表（引擎记录的玩家车速度、加速度、偏航率；语义视频里每辆车的位置和大小）、重绘的首帧和一条早期的总体 prompt；输出全程不变的每辆车和赛道外观、2–10 s 的阶段、0.3–2.5 s 带绝对时间戳的事件、每 0.5 s 的场景状态。每个评分跨度截取落在其中的事件并平移到跨度时钟，拼成模板 prompt。生成器整个会话仍只用一条 prompt，所以前缀缓存照样成立。
- 渲染器开发全程以 **SoL-Pi** 作为主编码智能体，用于数据准备、训练和评测。

### Fast Causal H3 VAE：智能体循环造出来的流式解码器（§3.2）

**原版解码器为什么不能用**：36 层 Transformer、2.42B 参数，为离线视频设计，依赖两种重叠：

- 空间分块：每帧切成 256 像素、至少重叠 64 像素的块再融合接缝，720p 要解 28 块，每个像素约算两次；
- 时间分块：一次解 5 个潜帧（17 个视频帧），同时还要读后面 2 个潜帧——要等尚未生成的潜帧，每个潜帧算 1.4 次。
- 720p 下每个 5 潜帧块约 870 ms（见"局限 / 存疑"里与图表的出入）。
- 小型流式解码器 TAE 约 10 ms，但在作者的流式运行里相对完整 VAE 只有 27 dB PSNR，细节保留 80%，草地、树叶、路面纹理逐帧闪烁。

**目标与约束（人只设一次）**：交给编码智能体（Claude Code）一个目标、四条约束——严格因果解码；每次调用输入 2 个潜帧；720p 下每次 ≤ 50 ms；从发布的 H3 VAE 权重出发。每轮迭代智能体提议 → 实现 → 跑同一套固定检查（与参考解码器逐位比对、扰动未来潜帧的因果性测试、延迟、相对 H3 VAE 的 PSNR / LPIPS / 细节）→ 由数字决定保留、回退或停止。**设定目标后约 3 小时**，因果解码器已经跑在流式管线里，之后继续蒸馏到收敛。

| 迭代 | 做了什么 | 结果 |
|---|---|---|
| 1 剪枝 | 不重训，贪心删层：每个深度删掉对重建 PSNR 损失最小的层并计时 | 36 层里留 24 层就满足 720p 和 540p 的 50 ms 预算；保留第 0–17、19–21、31、32、35 层原权重，1.62B 参数 |
| 2 因果化 | **时间**：每块 2 个潜帧，每层只看自己的 2 帧和缓存的前 4 帧 KV（约 0.7 s 视频），从不看后面的帧；每次调用输出 8 个视频帧，原生 5 潜帧块的首个潜帧仍出 1 帧，保持"5 潜帧 → 17 视频帧"。**空间**：去掉分块，改为 16×16 token 的不重叠窗口注意力（对应 256 像素），隔层平移半个窗口 | 训练前在非因果参考模式下与原版比对，误差在 2×10⁻⁵ 以内，改写本身不引入误差 |
| 3 测时间花在哪 | 朴素 PyTorch 720p 每 2 潜帧 146 ms，是预算的 3 倍；矩阵乘只占约 15 ms，其余是拷缓存和重分窗口（36 ms）、慢内核上的掩码注意力（30 ms）、大量小逐元素内核（30 ms，含每次把全部权重从 fp32 转 bf16）。对应改动：线性层权重一次存成 bf16（残差流保持 fp32）；KV 缓存按窗口放进预分配环形缓冲；分窗口 / 合并改成单次 index gather 并用 torch.compile 融合；注意力后端实测选 FlashAttention-4 变长接口（FlexAttention 带 block mask 每层 6 ms，24 层就超预算），每个窗口约 512 个 query 对 1,541 个 key；整块录成 CUDA graph 回放 | 37 → 32 ms（CUDA graph 这一步）；这些改动都不改变计算 |
| 4 平均指标漏掉的故障 | 4 个寄存器 token + 1 个类 token 看整帧、每块重建不缓存；第一版没给它们时间位置，而帧 token 用流中的绝对潜帧序号，导致从第 11 个潜帧起每个 5 潜帧块的首帧暗约 20 个灰度级——平均指标看不出来，是看解码视频发现的 | 给寄存器 token 加上所在块的时间位置后差距降到 2 个灰度级以内；新增两项检查：逐帧测块首亮度、从不同流时钟（0 / 100 / 1000）起解码结果完全一致 |
| 5 蒸馏到收敛 | 教师是同一潜变量的完整 H3 VAE 解码；学生用部署代码逐块解码，片段为 3 个 5 潜帧块（51 帧、384×384 裁剪），见到空缓存和满缓存两种块首。损失 = L1 + LPIPS（1.0）+ 帧差项（1.0，跨潜帧边界处 ×3）+ 边缘项（0.1）；8 卡、AdamW、lr 2×10⁻⁵，最后 3,500 步余弦降到 10⁻⁶ | 第 6,000 步停止（最后 500 步只涨 0.06 dB）；改任意未来潜帧，之前所有输出帧逐位不变 |
| 6 内核智能体 | 把 32 ms 版交给 Kernel Design Agents（KDA，用 Claude Code + Opus 5.5 在一个 GB200 节点上跑 2.5 小时），契约是对参考的正确性门限 + 延迟基准。改动：5 个全局 token 拼进 token 行使每个线性层只跑一次；qk-norm、RoPE、KV 写入融合成一个 Triton 内核；全局 token 注意力改 split-K Triton 内核；残差加与下一个 RMSNorm、SwiGLU 融进上投影 GEMM（quack）；fp32 输出头用 hi/lo 拆分做一次 bf16 张量核 GEMM；流状态移到 GPU 上，一个 CUDA graph 服务所有块 | 32 → 23.8 ms，其中矩阵乘约 14 ms；两个优化版与朴素 PyTorch 版相差 64–71 dB PSNR（bf16 舍入） |

**解码器对比**（"Fast Causal H3 VAE"图 (b)；质量是 3 个 768×1344 流式用例的平均，相对 H3 VAE 解码）：

逐步延迟（图 (a)，720p、2 潜帧/次、单张 GB200、同一脚本）：原版 326 → 块 2 因果 + 窗口注意力（仍 36 层）219 → 剪到 24 层 146 → FA4 变长注意力 + 打包 KV + bf16 权重 81.7 → torch.compile 融合 36.8 → CUDA graph 32.1 → KDA 融合内核 23.8 ms，合计 13.7×（540p 为 13.5×）。

**放进流式循环**：只替换视频解码器；参考帧的 TAE 编码器和两步 DiT 不变。接口一次收一个潜帧，凑够一对再解。在 768×1344、8 卡循环里，32 ms 版（KDA 之前）解 2 个潜帧用 36.8–37.3 ms，同一轮 DiT 用 264–329 ms；块首帧与 VAE 的差都不超过 2 个灰度级。

### 推理加速与部署（§3.3）

全部推理栈跑在 **Sol-Engine**（NVIDIA 的智能体原生视频生成全栈加速框架）上。

- **多卡并行**：8 卡，每卡常驻完整权重（推理中不收发权重）；Ulysses 式上下文并行——每个流式步的 token 序列切到 8 卡，FFN 在本地分片上算，注意力前用 all-to-all 按头重组，每卡对全序列算自己那部分头，再换回序列布局。

逐项累积消融（"Cumulative Inference Optimization"图：8 张 GB200、50 层、NFE = 2、优化后的流式编码器 / 解码器各阶段固定、P50 热启动延迟）：

| 优化 | DiT 延迟（ms） | 说明 |
|---|---|---|
| PyTorch 基线 | 799.66 | |
| + 静态上下文 KV 缓存 | 315.42 | 文本-图像条件、参考图、sink 的 KV 只算一次；**每个去噪时间步各自一份缓存**，只重算动态上下文 |
| + AdaLN 投影缓存 | 307.28 | 会话条件固定、去噪日程每块重复，shift / scale / gate 投影可复用；只缓存投影，不缓存激活 |
| + FlashAttention-4（形状感知调参） | 251.81 | Blackwell 优化内核，按流式推理的实际 Q / KV 形状调，每卡负载小，KV split 设为 1 |
| + 注意力元数据复用 | 224.10 | 序列长度、累积偏移、最大长度每次前向只准备一次，去掉逐层准备和主机-设备同步 |
| + 持久化 KV 布局 | **217.96** | KV 存在按内核读取布局排好的逐层持久缓冲里，静态部分写一次，动态部分原地更新 |

合计 3.67×。

**流式渲染各阶段**（"Streaming Render Latency"图和其 JSON；8 张 GB200 同一机架、参考 832×480、输出 1344×768、24 fps、两步生成）：

| 阶段 | 时间 |
|---|---|
| 参考编码 | 16.67 ms（P50） |
| 两步渲染（生成、采样器、缓存更新） | 217.96 ms（P50，含卡间通信） |
| 因果视频解码 | 23.8 ms（后来更新的解码器单独测得） |

图注和 JSON 明确写着：各阶段是**分别统计的中位数**，不是新测的端到端每块时间，不能直接相加；同一次运行里用旧解码器（36.54 ms）时，"RGB 就绪"的每块时间 P50 是 **272.73 ms**。

**发布形态**（README、模型卡）：

- 部署配置：50 层 DiT、checkpoint "1008b step224" 合并 LoRA 的 EMA 主干、2 次去噪评估、CFG = 1、S=2 / W=2 / C=2，启动 7 个调度单元；编码器为原生流式 TAE，解码器为"因果 ViT24"；不开注意力通信近似、层截断或其他改变质量的捷径。
- 需要 8 张卡在同一 NVLink 域内；Slurm 配置是 2 节点 × 4 卡并检查 NVL72 机架前缀。
- 权重包约 206.87 GB，重建合并主干还需 66.28 GB；五个模型组件：H3 渲染器主干、因果解码器、Qwen 条件模型（两种存储格式）、TAE、H3 音频编解码器。
- 60 个整理好的示例，默认 B10_e-track-3_bluehour；另有 Reactor 运行时集成，可用录好的语义视频 + 参考图 + prompt 在浏览器里逐块流式渲染（24 FPS 播放）。
- H3 推理里仍保留音频潜变量，但浏览器反馈路径**只发布 RGB 视频**。

## 局限 / 存疑

- **作者自己写的局限**（"Current Limitations and Future Directions"）：
  - **只有一个场景**：渲染器、两步学生、评委都只在赛车数据上训练，第三人称追尾相机；测试驾驶来自同一游戏，模型是拟合在这个场景上的。接口本身不限于赛车，扩到更多游戏、量化每个新场景需要多少数据是下一步。
  - **渲染器太大**：仍是完整 MiniMax-H3 DiT 跑在 8 张卡上；要减参数、降单步成本、提升画质。
- **没有渲染质量评测**：没有对比其他渲染器或基线，没有结构一致性（语义图 vs 生成画面）的指标，也没有消融（如去掉 Resampling Forcing、去掉引导拟合、去掉时间线 prompt 各掉多少）。"有时把语义视频倒着渲染"这类现象只是定性描述。
- **原版 VAE 的基线数字前后不一（需核对）**：§3.2 正文说原版 720p 每个 5 潜帧块约 870 ms，折成 2 潜帧约 348 ms；解码器对比图写 326 ms（"5 latent frames per call, scaled to 2"）；智能体循环示意图写 324 ms。13.7× 是按 326 算的。
- **迭代顺序与逐步延迟图不同**：正文是先剪枝（迭代 1）后因果化（迭代 2）；逐步延迟图 (a) 却是先"块 2 因果 + 窗口注意力（36 层）219 ms"再"剪到 24 层 146 ms"。可能只是图按另一顺序重排了消融，页面没说明。
- **"258 ms/块"不是实测**：专题清单和 Matrix-Game 4.0 表 3 记的"258 ms/块、两块约 517 ms"看起来是把三个阶段中位数 16.67 + 217.96 + 23.8 相加；页面 JSON 明确说阶段值不可相加，同次运行实测的 RGB 就绪每块 P50 是 272.73 ms（用的是 36.5 ms 的旧解码器）。另外解码器放进循环时那一轮 DiT 用了 264–329 ms，也高于 217.96 ms 的消融值，说明各数字来自不同运行。
- **"720p"与 1344×768**：解码器指标标的是 720p，部署输出是 1344×768（768p）。循环里的解码时间（36.8–37.3 ms）是在 768×1344 上测的。
- **训练目标是 H3 自己生成的**：预训练拟合的是原版 H3 Ref2VA 25 步生成的视频，DMD 的真评委也是原版 H3，所以学生的画质上限基本就是 H3 在这类条件下的表现；而作者自己发现原版 H3 超过约 5 s 就不再紧跟语义视频和参考图，靠 5 s 一段续写来规避。
- **长时一致性的证据有限**：sink 只有 2 个调度单元，近期历史 2 个；离开视野再回来的物体（如对手车涂装）靠参考图、prompt 和近期输出维持，页面只给了 1 分钟的定性视频。语义图里所有对手车同色，渲染器要自己区分是哪辆，页面承认这一点但没有量化。
- **参考图依赖外部模型**：训练用 GPT-Image-2.5 重绘，prompt 由 Claude Opus 5.5 和 GPT-6.1 Sol 智能体写；部署时参考图是离线准备的资产。新场景的参考图怎么来、质量如何影响结果，没有讨论。
- **硬件门槛**：8 张 GB200（同一 NVLink 域）服务一个会话，与 [[topics/notes/代码世界模型与神经渲染/1-11_Matrix-Game-4.0|Matrix-Game 4.0]] 的单张 RTX 5090 差距很大。
- **音频**：H3 推理里保留音频潜变量，演示视频带声音，但浏览器实时路径只发 RGB。演示里的声音是怎么来的页面没说。
